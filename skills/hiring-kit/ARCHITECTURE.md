# Архітектура HR-модуля найму на 20/80

Референс — модуль найму AI Advisory Board (Next.js + Prisma + Postgres, Telegraf-бот на
вебхуку, адмінка на server actions). Стек — деталь; переносяться **сутності, стан-машина,
контракт анкети, порядок кроків і сторожі**. Студентський Claude пише це в тому стеку, який
уже є в проєкті.

## 1. Схема

```
Оголошення вакансії (Telegram-канал / job-борд / сайт / особисте повідомлення)
   │  посилання t.me/<бот>?start=anketa_<роль>
   ▼
[A] Бот: /start anketa_<роль> → Candidate (upsert за telegramId) + Application(stage=anketa)
   │  крок за кроком: текст / посилання / число / кнопка / чекбокси; пауза і продовження
   │  кожне повідомлення в обидва боки → Event(message_in | message_out)
   ▼
[B] Завершення: бали за треками + gatesFailed → Application(status=completed, stage=screened)
   │  → «Дякую, відповім протягом двох робочих днів» кандидату
   │  → картка власнику в Telegram: бали, смуга, гейти, години, ставка, посилання в адмінку
   ▼
[C] (опційно) LLM-шар доказів для текстових відповідей → цитати, прапори, суперечності
   ▼
[D] Канбан: власник рухає картку screened → interview → test → offer → hired
   │  reserve / rejected — лише з причиною; кожна мутація → Event(stage_change | verdict)
   │  дзвінки, листи, відповіді з особистого Telegram → Event вручну з картки
   ▼
[E] Пул: нова вакансія → фільтр (роль, бал, причина, давність, згода)
        → персональний текст на кожного → відправка ПО ОДНОМУ → Event(message_out, invite)

[F] Імпорт (JSON з job-борда / чату / таблиці) → дедуп → Candidate(consentRecontact=false)
        + Application(status=imported, stage=new) + Event(import)
```

## 2. Сутності

**Candidate — людина.** Одна на `telegramId`; до того як людина напише боту — одна на
@username / телефон / email (дедуп імпорту). Поля: імʼя, @username, телефон (нормалізований
`+380…`), email (нижній регістр), місто, посилання `[{kind, url}]`, ролі, теги,
`consentRecontact`, джерело, `firstSeenAt`, `lastContactAt` (останнє повідомлення В
БУДЬ-ЯКИЙ БІК — рухають лише `message_in`, `message_out`, `call`, не нотатки).

**Application — заявка на роль.** Треки (ролі), відповіді `{ключ: значення}`, бали
`{трек: число}`, `gatesFailed[]`, статус анкети (`in_progress | completed | cancelled |
imported`), поточний крок, джерело (payload посилання — це атрибуція), стадія, вердикт,
причина, нотатка, `nextActionAt`, `stageChangedAt`. `telegramId` необов'язковий — імпортована
заявка приходить без Telegram. На людину — одна активна анкета; старіші рядки — історія.

**Event — історія.** `kind`: `message_in | message_out | stage_change | verdict | note |
call | import`; `channel`: `telegram_bot | telegram_personal | email | phone | robota |
admin`; текст (≤ 4 000), `meta` (JSON: `{from, to, reason}`, `{invite: роль}`,
`{question: ключ}`), `actor`: `bot | candidate | admin:<email>`, `at`. Пишеться ботом (кожне
повідомлення анкети) і КОЖНОЮ мутацією адмінки.

Референс-схема (Prisma, наша продова, скорочені лише коментарі):

```prisma
model HiringCandidate {
  id               String              @id @default(uuid())
  telegramId       BigInt?             @unique
  telegramUsername String?
  fullName         String?
  phone            String?             // нормалізований: +380…
  email            String?             // нижній регістр
  city             String?
  links            Json                @default("[]") // [{kind:'portfolio'|'robota'|'linkedin'|'other', url}]
  roles            String[]            @default([])
  tags             String[]            @default([])
  consentRecontact Boolean             @default(true) // true лише для тих, хто сам написав у бот; імпорт ставить false явно
  source           String?             // 'bot'|'telegram'|'robota.ua'|'import'|...
  firstSeenAt      DateTime            @default(now())
  lastContactAt    DateTime?           // останнє повідомлення в будь-який бік
  createdAt        DateTime            @default(now())
  updatedAt        DateTime            @updatedAt
  applications     HiringApplication[]
  events           HiringEvent[]

  @@index([lastContactAt])
  @@index([phone])
  @@index([email])
  @@index([telegramUsername])
}

model HiringApplication {
  id               String           @id @default(uuid())
  telegramId       BigInt?
  telegramUsername String?
  fullName         String?
  tracks           String[]         @default([])     // 'video' | 'sales' | 'mkt'
  answers          Json             @default("{}")   // { qkey: value | value[] | null }
  scores           Json             @default("{}")   // { video: 71 } — лише обрані треки
  gatesFailed      String[]         @default([])
  status           String           @default("in_progress") // in_progress | completed | cancelled | imported
  currentStep      String?          // qkey поточного питання; "_roles" — вибір ролей
  source           String?          // start payload
  completedAt      DateTime?
  candidateId      String?
  candidate        HiringCandidate? @relation(fields: [candidateId], references: [id], onDelete: SetNull)
  stage            String           @default("new")  // new|anketa|screened|interview|test|offer|hired|reserve|rejected
  verdict          String?          // yes | maybe | no
  verdictReason    String?
  verdictNote      String?
  nextActionAt     DateTime?
  stageChangedAt   DateTime?
  createdAt        DateTime         @default(now())
  updatedAt        DateTime         @updatedAt
  events           HiringEvent[]

  @@index([telegramId])
  @@index([status, createdAt])
  @@index([candidateId])
  @@index([stage])
}

model HiringEvent {
  id            String             @id @default(uuid())
  candidateId   String
  candidate     HiringCandidate    @relation(fields: [candidateId], references: [id], onDelete: Cascade)
  applicationId String?
  application   HiringApplication? @relation(fields: [applicationId], references: [id], onDelete: SetNull)
  kind          String             // message_in | message_out | stage_change | verdict | note | call | import
  channel       String?            // telegram_bot | telegram_personal | email | phone | robota | admin
  text          String?
  meta          Json?
  actor         String?            // 'bot' | 'admin:<email>' | 'candidate'
  at            DateTime           @default(now())

  @@index([candidateId, at])
  @@index([applicationId, at])
}
```

Для нового проєкту: `consentRecontact` краще зробити `@default(false)` і ставити `true`
явно в боті — тоді забутий прапорець у новому шляху створення кандидата не дає згоди
мовчки. Стадії, статуси, вердикти — рядки, а не enum БД: значення стабільні, підписи
переписуються без міграції; перелік і перевірки — в одному модулі коду.

## 3. Стан-машина стадій

```
new → anketa → screened → interview → test → offer → hired
  └──────────── будь-яка ────────────► reserve | rejected   (лише з причиною)
```

- **Бот (`system`)** рухає заявку лише на ОДИН крок уперед основним шляхом (старт анкети →
  `anketa`, завершення → `screened`) або в бічні стадії.
- **Адмін** — у будь-яку іншу стадію, зокрема назад (кандидат повернувся з резерву,
  помилкове перетягування); рух назад по основному шляху канбан підтверджує діалогом.
- **Вердикт ставиться разом із бічною стадією:** `rejected → no`, `reserve → maybe`; окремо
  з картки — `yes | maybe | no`.
- **Причини** (стабільні ідентифікатори): `price_too_high`, `low_hours`, `no_portfolio`,
  `weak_craft`, `no_reply`, `took_other_job`, `overqualified`, `not_now`, `wrong_role`,
  `other`. Для `other` нотатка обов'язкова — «Інше» без тексту нічого не скаже повторному
  контакту через пів року.
- **Умовний запис:** `UPDATE … WHERE id = ? AND stage = <очікувана>`; 0 рядків → `conflict`
  («картку вже перемістили — оновіть сторінку»). Результат зміни — типізований:
  `not_found | invalid_transition | needs_reason | needs_note | conflict`, кожен має
  людський текст. Мовчазний `return` заборонений.

## 4. Контракт анкети

Один конфіг — єдине джерело правди для бота, скорингу й адмінки (адмінка показує відповіді
рівно в порядку бота).

```ts
type QuestionKind = "text" | "url" | "choice" | "multi" | "number";
interface Question {
  key: string;                    // стабільний, лягає в БД
  track: "common" | <роль>;
  phase?: "start" | "end";        // лише для common: на початку чи наприкінці
  text: string;
  kind: QuestionKind;
  options?: { label: string; value: string; pts: number }[]; // value стабільне, label — ні
  gate?: boolean;                 // обов'язковий по суті; пропуск → gatesFailed
  optional?: boolean;             // можна пропустити без позначки
  short?: string;                 // назва для картки: «портфоліо», «ціна за ролик»
  showIf?: { key: string; equals: string }; // умовне питання
}
```

- **Порядок:** common-початок (імʼя, місто, телефон) → треки обраних ролей у канонічному
  порядку → common-кінець (години, ставка, старт, питання кандидата).
- **Типи:** `text` (≤ 2 000 знаків), `url` (приймає і `youtube.com/…` без протоколу),
  `number` (гроші: «25 000», «25к», «1,5 тис» → число; діапазон «800–1200» → нижня межа),
  `choice` (кнопки), `multi` (чекбокси ✅/⬜ + «Далі»).
- **Пара «текст + самокласифікація»:** текстове питання-доказ («Ваш кейс із цифрою…»), за
  ним кнопка «Цифра вище — точна / приблизна / цифр немає» з балами. Текст — для людини і
  LLM-перевірки, кнопка — для детермінованого бала.
- **Гейти:** 3–4 на роль, кожен закриває помилку, яку ви вже бачили (закрите портфоліо,
  ціна лише «за місяць», нереальні години, анкета без відповідей).
- **Ваги і пороги:** скоркарта з 4 блоків на 100 балів (напр. 40/20/20/20) + бонуси/штрафи
  понад 100; пороги ≥ 65 співбесіда, 50–64 резерв, < 50 відмова (калібруються після перших
  20 анкет). Бали common-питань додаються до КОЖНОГО обраного треку.

## 5. Скоринг — «доказовий»

Шар 1 — **детермінований** (є в нас у проді): бал = сума `pts` обраних варіантів треку +
common; `gatesFailed` = gate-питання без відповіді; смуга = поріг. Пояснення кожного бала =
обраний варіант, видно в картці поруч із відповіддю. Незавершена анкета показує частковий
бал наживо з позначкою «частковий»; імпортована — без балів.

Шар 2 — **LLM-докази** (рекомендований наступний крок; промпт — `prompts.md` §3): для
текстових відповідей і резюме модель повертає бал за КОЖНИМ критерієм скоркарти з дослівною
цитатою-доказом, прапор `noEvidence`, суперечності (кнопка «точна цифра» при тексті без
цифри), питання для співбесіди. Правила: бал > 0 лише з цитатою; критерії — лише із
затвердженої скоркарти, версія скоркарти в результаті; жодних «загальних вражень»; результат
LLM не переписує стадію і не ставить вердикт — лише підсвічує.

Людині лишається: затвердження скоркарти, пограничні кандидати, портфоліо і тестове,
компенсація, фінальне рішення.

## 6. Бот-анкета

- **Вхід — deep-link** `t.me/<бот>?start=anketa` (вибір ролей кнопками) або
  `anketa_<роль>` / `anketa_<роль1>_<роль2>`. Невідомі хвости не вгадують роль, але лишаються
  в `source` для атрибуції каналу. Посилання будуються однією функцією, юзернейм бота ніде
  руками не пишеться.
- **Крокова машина — чисті функції:** `buildSequence`, `activeSequence` (з урахуванням
  `showIf`), `nextStep` (умову перевіряти на ВЖЕ оновлених відповідях), `resumeStep`
  (якщо крок перейменували — перше питання без відповіді), `stepPosition` («Питання 5 з 32»).
- **Кнопки:** `callback_data` = `hq:<ключ>:<індекс>` (≤ 64 байт); кнопка під уже пройденим
  питанням відповідає «Це питання вже пройдене» і нічого не переписує. Мітка довша за ~30
  знаків — варіанти нумерованим списком у тексті, на кнопці номер. Після відповіді кнопки
  зникають, під питанням лишається «→ обране».
- **Пауза і продовження:** `/cancel` або будь-який інший `/start` → статус `cancelled` з
  збереженим кроком; те саме посилання → «Продовжити / Почати заново». Незавершена анкета
  перехоплює звичайні повідомлення лише 48 год від останнього руху.
- **Подвійний тап:** крок просувається умовним записом `WHERE currentStep = <цей крок>`;
  наступне питання шле лише той виклик, чий запис пройшов.
- **Вебхук завжди відповідає 200:** усі обробники в try/catch; збій історії не ламає
  анкету; лог повідомлення пишеться ПІСЛЯ успішного надсилання.
- **Картка власнику** після завершення — одразу, без нічної тиші (це відповідь на дію
  кандидата): імʼя · @username · місто; бали по треках зі смугою; гейти; години · ставка ·
  старт; посилання на картку в адмінці.

**Чому бот, а не форма на сайті.** Кандидати малого бізнесу в Україні вже в Telegram; бот
відкривається з того самого оголошення без переходу в браузер, питає по одному (кнопки на
телефоні), тримає паузу і — головне — дає `telegramId`: з ним можна відповідати по стадіях
і повторно написати через пів року. Форма дає лише email, на який не відповідають.

## 7. Канбан і картка кандидата

- **Одна картка = один кандидат**, стадія — його найсвіжішої заявки. Колонки — основні
  стадії без `hired`; «Найнято / Резерв / Відмова» згорнуті праворуч лічильниками.
- **Картка на дошці:** імʼя, @username, ролі, бал (макс. серед заповнених анкет або
  частковий), днів без контакту (червоне понад 3), наступна дія, вердикт, кількість заявок.
- **Перетягування** в резерв/відмову відкриває модалку причини; назад — підтвердження.
- **Сторінка кандидата:** відповіді кожної заявки в порядку бота з балами і гейтами; історія
  (таймлайн Event); форми: зміна стадії, вердикт + причина + нотатка, нотатка / дзвінок /
  повідомлення з особистого Telegram / лист / відповідь кандидата (контакт рухає
  `lastContactAt`, нотатка — ні), наступна дія з датою (локальний час власника, не сервера),
  згода на повторний контакт. Кожна форма повертає `ok` або `err` текстом.

## 8. Повідомлення по стадіях

Тексти — `prompts.md` §4. Чесний стан у нас: автоматично йде лише подяка після анкети,
запрошення пулу — кліком; решта стадійних повідомлень писалась руками, і саме тому 88
відгуків тижнями лишались без відповіді. Тому в студента це будується одразу. Механіка на
20/80: при зміні стадії картка пропонує шаблон відповідного повідомлення, власник править і
надсилає кліком; відправка — через бота (якщо кандидат писав боту) або фіксується як Event з
каналом, яким власник надіслав сам. Автоматично без людини — лише підтвердження завершення
анкети. Нічна тиша 23:00–09:00 для всього, що ініціює власник; відповіді на дію кандидата —
одразу.

## 9. Пул і повторний контакт

- **Фільтри (GET-параметри):** роль, мінімальний бал, причина минулого вердикту, «без
  контакту понад N днів» (кандидат без жодного контакту вважається давнім), згода — за
  замовчуванням лише зі згодою, зняти можна лише явно.
- **Сортування:** бал за спаданням, далі найдавніший контакт першим.
- **«Підготувати запрошення на роль»** генерує персональний текст на кожного (до 100 за
  раз): коли подавався і на що, «чому саме ви» з причини минулого вердикту (`not_now` /
  `took_other_job` → «тоді було не на часі»; `price_too_high` → «обговорити умови заново»;
  `low_hours`; `wrong_role`) і балу (≥ поріг співбесіди → «один із найсильніших
  результатів»), посилання на анкету саме цієї ролі. Текст редагується в рядку.
- **Відправка ПО ОДНОМУ** з серверними перевірками: текст непорожній і ≤ 4 096; не нічна
  тиша; кандидат існує; є `telegramId` (писав боту); `consentRecontact = true`; те саме
  запрошення на ту саму роль не надсилалось останні 10 хв. Відповідь Telegram «blocked /
  deactivated / chat not found» → людський текст «кандидат заблокував бота».
- **Відповідь кандидата** боту поза анкетою протягом 14 днів після контакту лягає в його
  історію.

## 10. Імпорт

- **Формат запису:** `{fullName, telegramUsername?, phone?, email?, city?, roles[], source,
  links[], note?, appliedAt?}`; до 5 000 записів за раз; вхід — API для адміна і локальний
  скрипт із dry-run за замовчуванням (`APPLY=1` для запису), ненульовий код виходу при
  помилках, статус 207 при частковому успіху.
- **Нормалізація:** @username з `t.me/…` чи `@…` (4–32 символи `[A-Za-z0-9_]`); телефон
  `0XXXXXXXXX` → `+380XXXXXXXXX`, `80XXXXXXXXX` → `+380…`, менше 10 цифр — не телефон; email
  у нижній регістр; посилання лише `http(s)`, без дублів.
- **Без контакту не імпортуємо:** запис без @username, телефону і email відхиляється з
  причиною (у нас 21 картка robota.ua з 77 мала закриті контакти — вони лишились у файлі
  «написати через чат борда», а не в базі).
- **Дедуп:** @username → телефон → email (від найнадійнішого). Знайдено — дописуємо лише
  порожні поля, ролі й посилання зливаються; не знайдено — новий кандидат з
  `consentRecontact = false`. Повторний імпорт того самого файлу не створює заявку, якщо є
  `imported` з тим самим джерелом і датою подачі.
- **Людина, яка потім напише боту** з тим самим @username, привʼязується до імпортованого
  кандидата (у нього зʼявляється `telegramId`), а не створює дубль.
- Імпорт НЕ створює лідів у CRM продажів.

## 11. Сторожі

1. Згода перед будь-яким проактивним повідомленням — перевірка на сервері.
2. Бот не може написати першим тому, хто йому не писав (обмеження Telegram Bot API):
   кнопка «надіслати через бота» для кандидата без `telegramId` відповідає «Кандидат не
   писав боту», перший контакт — з особистого акаунта / пошти / чату job-борда з
   посиланням на анкету, і фіксується Event вручну.
3. Резерв і відмова — лише з причиною; «Інше» — лише з нотаткою.
4. Умовний запис стадії й кроку анкети (конфлікт, подвійний тап).
5. Нічна тиша 23:00–09:00 на запрошення пулу і будь-які повідомлення з ініціативи власника.
6. Дедуп повторного кліку «надіслати» (10 хв) і повторного імпорту.
7. Доступ до найму — лише ролям власника/адміна; підтримка й менеджери інших відділів
   отримують 403 навіть з адмін-сесією.
8. Кожна мутація адмінки — Event з `actor = admin:<email>`.

## 12. Приватність

- Персональні дані кандидатів (файли імпорту, вивантаження з job-бордів, резюме) — поза
  git: тимчасова тека або зашифроване сховище; у репо — лише формат і скрипт.
- Строк зберігання: файл імпорту видаляється після успішного `APPLY=1` і звірки лічильників;
  дані кандидатів у базі — задайте строк у `RUNBOOK.md` (напр. 24 місяці від останнього
  контакту — стільки ж, скільки живе цінність пулу) і процедуру видалення на прохання
  кандидата (видалення Candidate каскадом видаляє Event).
- Згода на повторний контакт — окремий прапорець, який кандидат може зняти словами «не
  пишіть мені» → власник знімає з картки, це теж Event.
- У LLM-скоринг не передавати телефон, email, @username — лише відповіді й текст резюме.

## 13. Технічні рішення за замовчуванням (для ТЗ у проєкті студента)

- **Стек — той, що вже є** в проєкті (будь-яка мова, будь-яка SQL-база). Немає бекенду —
  найпростіший: Node/TypeScript + Postgres (або SQLite для одного власника) + ORM з
  міграціями.
- **Telegram-бот** через токен від @BotFather у `.env` (`TELEGRAM_BOT_TOKEN`), вебхук на
  сервері (або long polling для локального старту); `ADMIN_TELEGRAM_ID` — кому йде картка.
- **Ролі адміна:** owner/admin бачать найм; решта — 403. Одна сесія, без SSO.
- **Cron не потрібен:** бот реагує на повідомлення, пул — на клік, нічна тиша перевіряється
  в момент відправки, `nextActionAt` видно на картці.
- **Конфіг ролей, питань і скоркарти** — у коді (один файл на модуль), а не в адмінці:
  зміна анкети = коміт із історією; `value` варіантів не перейменовувати.
- **Тести** — на чисті функції: крокова машина, розбір відповідей, бали, гейти, стадії,
  дедуп, нормалізація, текст запрошення, довжина `callback_data`.
- **LLM-шар доказів** — будь-яка модель з JSON-режимом (у студента вже є Claude; дешево —
  NVIDIA NIM / локальна), виклик при завершенні анкети, результат — окрема JSON-колонка.
