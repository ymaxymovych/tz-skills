# Адаптація досьє під бізнес студента — інтерв'ю і схема

Наша картка досьє (див. `prompts.md` розділ 2) відлагоджена під ОДИН бізнес: продаж
корпоративного навчання роботі з AI. Половина її полів — про НАШУ пропозицію («де допоможе
AI», «як переформулювати оффер в нашій ідеології»). У консультанта, виробника чи сервісної
компанії ці поля мають бути ІНШИМИ, і тому скіл спершу проводить інтерв'ю, а вже з відповідей
будує `docs/lead-enrichment/DOSSIER_SCHEMA.md` — схему саме для цього бізнесу.

## Правила інтерв'ю (як у /tz-draft)

- Усі питання — ОДНИМ повідомленням, кожне з трьома варіантами і рекомендацією (✅), з
  поясненням, чому саме вона. Користувач відповідає одним рядком («1б, 2а, 3 — своя
  відповідь…»); пропущені беруть рекомендацію. «ФІНІШ» = прийняти всі рекомендації.
- Спершу подивись на проєкт: сайт, CRM, наявні ліди, README — усе, що видно з коду й
  даних, НЕ питай. Питай лише те, чого в проєкті немає.
- Технічне (СУБД, мова, крон, де ключі) — вирішуй сам за `ARCHITECTURE.md` §9.

## Питання (10; пропускай ті, на які проєкт уже відповідає)

1. **Що саме ви продаєте і кому** (одним реченням) і **яка одна дія — успіх дзвінка**
   (зустріч / КП / замовлення / демо / пробна партія)?
   Навіщо: визначає поле `sales.nextStepGoal` і те, під що пишеться `callOpener`.
2. **Хто у клієнта приймає рішення про вашу покупку** (власник / директор / закупівельник /
   технолог / HR / маркетолог) і **хто зазвичай залишає заявку** (той самий чи інша роль)?
   Навіщо: `person.likelyRole` + `person.decisionPower` калібруються під ЦЮ роль, а не
   під «власник» за замовчуванням.
3. **Ідеальний клієнт — три ознаки** (галузь, розмір, географія, обсяг, наявність чогось)
   і **три дискваліфікатори** (надто малий, конкурент, не та країна, держсектор…)?
   Навіщо: `sales.fitSignals[]`, `sales.redFlags[]` і формула `leadScore`.
4. **Які 3–5 болів клієнта ви реально закриваєте** (мовою клієнта, не вашою)?
   Навіщо: `sales.likelyPains[]` шукаються під ці болі, а не «багато ручної роботи».
5. **Що у бізнесі клієнта треба ПОБАЧИТИ, щоб ваша пропозиція стала очевидною?**
   (консалтинг: ознаки зростання/кризи, вакансії, нові напрямки; виробництво: що і в
   яких обсягах вони закуповують, тендери, сертифікати; послуги: сезонність, скарги,
   відгуки; SaaS: який софт уже використовують.)
   Навіщо: це заміняє наше «Де допоможе AI» на ВАШЕ поле `rich.opportunities[]` — назва
   секції картки береться з відповіді.
6. **Які реєстри й публічні джерела важливі у вашій країні/галузі** (держреєстр юросіб,
   тендери, ліцензії, галузеві каталоги, відгуки, вакансії, соцмережі)?
   Навіщо: список «власних перевірок» воркера і промпт двигунів.
7. **Що з досьє має бути видно на картці ПЕРШИМ** (вердикт і оцінка / контакти /
   масштаб / зачіпки) і **хто читає картку** (ви / менеджер / кол-центр / бот)?
   Навіщо: порядок секцій і довжина `tldr`.
8. **Скільки лідів на день/тиждень і звідки** (форма, реклама, LinkedIn, Telegram, ручний
   імпорт)? Навіщо: стеля викликів на добу, розклад крона, які поля є на вході.
9. **Мова досьє і мова клієнтів** (українська / англійська / кілька)? Навіщо: промпти й
   формати телефонів у пошуку.
10. **Що робити з лідом, про якого нічого не знайшлось** (дзвонити «сліпо» / знизити
    пріоритет / не дзвонити)? Навіщо: `confidence: low` має вести до конкретної дії.

## Схема: що фіксоване, що адаптивне

**Фіксований кістяк** (однаковий для всіх, бо перевірений на 234 досьє):
```
summary, confidence, caveats, sources[]
person   {likelyRole, seniority, decisionPower, communicationStyle}
company  {industry, whatTheyDo, sizeBand, model, legalEntity?, registryId?, city}
scale    {teamInterpretation, maturityStage, revenueGuess}
rich     {tldr, identityEvidence, businessLines[], namedClients[], geography,
          callOpener, qualifyingQuestions[], leadScore{value, reasoning}}
```
Правила: `confidence` не `high` при непідтверджених полях; група ≠ юрособа; збіг ПІБ —
не ідентифікація; цифри лише з джерел.

**Адаптивна частина** (заповнюється з інтерв'ю):
```
sales.nextStepGoal        ← Q1 (яка дія = успіх дзвінка)
sales.fitSignals[]        ← Q3 (ознаки ідеального клієнта — знайдені/не знайдені)
sales.redFlags[]          ← Q3 (дискваліфікатори)
sales.likelyPains[]       ← Q4 (лише ці болі, мовою клієнта)
sales.suggestedOffer      ← Q1+Q4 (який ваш продукт/пакет пасує і чому)
rich.opportunities[]      ← Q5 (назва секції з відповіді: «Що вони закуповують»,
                             «Де застосовна наша експертиза», «Який софт уже стоїть»…)
                             елемент: {area, evidence, whyItMatters, howToRaiseOnCall}
rich.offerReframe         ← Q1+Q4 (як подати пропозицію саме цьому ліду)
leadScore.formula         ← Q3: +2 за кожен fitSignal, −3 за redFlag, ×0.5 при confidence low
checks[]                  ← Q6 (реєстри й джерела для власних перевірок, з URL-шаблонами)
card.order[]              ← Q7 (порядок секцій картки)
policy.noDataAction       ← Q10
```

## Що робить скіл після інтерв'ю

1. Пише `docs/lead-enrichment/DOSSIER_SCHEMA.md`: кістяк + адаптивні поля з ПРИКЛАДОМ
   заповнення для одного реального ліда користувача (не вигаданого).
2. Генерує промпт двигунів і промпт синтезу з `prompts.md`, підставивши блок «НАША
   ПРОПОЗИЦІЯ» (Q1, Q4), ролі (Q2), реєстри (Q6), мову (Q9).
3. Будує картку у CRM користувача за `card.order[]`. Наша картка (для орієнтиру): рядок
   вердикту (tldr + leadScore + confidence + «досьє N днів») → 👤 Особа → 🏢 Компанія →
   📈 Масштаб → 🎯 Кут продажу (болі, підхід, зачіпки, red flags) → Напрямки бізнесу →
   [адаптивна секція з Q5] → Сценарій дзвінка (opener + питання) → 🔗 Джерела → кнопка
   «скопіювати досьє одним текстом» (для месенджера) → згорнуті сирі відповіді двигунів.
4. Показує користувачу перше досьє і питає ОДНИМ повідомленням, що прибрати/додати.
   Друга ітерація схеми — остання; далі схема версіонується (`version` у досьє), і
   ліди зі старою версією потрапляють у чергу на регенерацію.
