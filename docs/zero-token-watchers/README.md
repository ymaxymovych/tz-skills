# Плейбук: безтокенні сторожі — чат-оркестратор прокидається лише на подію

Мета: залишити LLM-чату рішення та дії, а очікування передати дешевим скриптам. Студент або команда іншого проєкту може повторити цей спосіб для Telegram, логів, завершення задач і потрібних слотів статусу.

Походження: 2event, 12.10.2026, Ярослав. Чат-оркестратор Claude Code прокидався кожні 30 хвилин, щоб «перевірити Telegram і фабрику»: 48 пробуджень на добу. Кожне знову читало весь контекст — у довгому чаті десятки тисяч токенів. Рішення: чат будять лише безтокенні сторожі, які завершуються на справжній події або потрібному слоті статусу.

## 1. Принцип: світ опитує скрипт

LLM-чат не має опитувати світ сам. Bash/Python-скрипт перевіряє джерело без виклику моделі й витрачає нуль LLM-токенів під час очікування.

У Claude Code скрипт запускається через Bash tool з `run_in_background=true`. Завершення фонової задачі будить чат і передає її вивід.

**Один сторож = одна подія = одне пробудження.** Сторож може багато разів перевіряти джерело всередині свого процесу, але завершується рівно один раз.

Послідовність роботи:

1. Чат запускає сторож у фоні та чекає.
2. Скрипт сам опитує джерело, поки немає події.
3. На подію друкує короткий результат і виходить.
4. Чат читає результат, діє та однією командою запускає наступний сторож.

Heartbeat-циклів усередині чату немає. Очікування не потребує регулярного повідомлення «усе ще чекаю».

## 2. Сторож подій фабрики

Готовий зразок 2event: `~/tz-skills/docs/zero-token-watchers/watch.sh.example`.

Він стежить через `tail` за логами `fixloop3.log` і `stage_deploy.log`, відбирає через `grep` події, які потребують втручання:

- `needs a hand`;
- `ended: (blocked|failed)`;
- `review-failed`;
- `BASE BROKEN…`.

Відомий шум відсіюється змінною `IGNORE`: це regex, який передають при запуску. Не треба змінювати код сторожа під кожен відомий виняток.

Той самий сторож перевіряє, що ключові процеси фабрики живі. Зупинка процесу теж має стати подією, яку побачить оркестратор.

На подію скрипт друкує `EVENT …` і виходить. Чат читає три рядки виводу, вирішує проблему та перезапускає сторож однією командою.

Для іншого проєкту взяти цей файл як шаблон і підставити свої логи, патерни, винятки та процеси. Патерн має означати потребу в дії.

## 3. Сторож Telegram

Готовий скрипт: `~/tz-skills/docs/zero-token-watchers/tg_watch.py` — близько 120 рядків, Telethon.
Інструкція: `~/tz-skills/docs/zero-token-watchers/README.md`.

Він використовує той самий `StringSession`, що й telegram-mcp, з `теки вашого telegram-mcp (`.env`; шлях задається `--env` або змінною `TELEGRAM_MCP_ENV`)`. Сесію залишають локально; у плейбук або git її значення не копіюють.

Раз на п'ять хвилин скрипт виконує `get_messages(chat, min_id=last_seen)` для вибраних чатів.

- Ігнорує власні повідомлення з підписом `— Відправлено моїм AI-помічником`.
- Зберігає стан у `%LOCALAPPDATA%/tgwatch/state.json`.
- Перший запуск фіксує поточну межу читання тихо, щоб історія не стала новою подією.
- Нові повідомлення друкує у вивід і завершується з кодом `0`.
- У заданий слот друкує `TICK HH:MM status_slot=yes` і завершується з кодом `0`.
- Помилка мережі або авторизації завершує скрипт з кодом `3`.

Команда запуску; замінити `<id1,id2>` на ID потрібних чатів:

```bash
uv --directory ~/telegram-mcp run python ~/tz-skills/docs/zero-token-watchers/tg_watch.py --chats <id1,id2> --interval 300 --until 00:00,06:00,12:00,18:00
```

Цю команду чат запускає через Bash tool з `run_in_background=true`.
`--interval 300` задає частоту перевірки скриптом; `--until` — потрібні слоти статусу.

Після завершення чат розрізняє нове повідомлення, слот статусу та помилку. Для коду `3` спершу з'ясовує причину, щоб не створити цикл миттєвих перезапусків.

## 4. Слот-таймер: запасний варіант

Старий `tick.sh` робив `sleep` до найближчих `:00` або `:30`, потім завершувався й будив чат.

Він лишається запасним варіантом. У поточному способі його замінив `--until` у `tg_watch.py`: один процес чекає і повідомлення, і заданого часу.

Слот потрібен для конкретного статусу, який команда справді очікує. Пробудження «просто подивитися» не є причиною додавати таймер.

## 5. Економіка пробуджень

| До | Після |
|---|---|
| 48 пробуджень на добу через кожні 30 хвилин | 4 слоти статусу + реальні повідомлення + реальні події фабрики |
| Чат щоразу перевіряє джерела та перечитує контекст | Джерела перевіряють скрипти; чат отримує коротку подію |

Кожне пробудження читає весь контекст. У довгому чаті це десятки тисяч токенів навіть тоді, коли новин немає.

За приблизно однакового розміру контексту вартість очікування пропорційна кількості пробуджень, а не виконаній роботі. Без реальних подій 48 → 4 означає у 12 разів менше пробуджень; події додаються до цих чотирьох.

«Безтокенний» стосується роботи сторожа. Пробудження чату, розбір події та подальші дії витрачають токени.

## 6. Правила проєктування сторожа

1. **Виходити один раз на подію.** Після обробки чат запускає новий процес.
2. **Друкувати не більше 10 рядків.** Чат прочитає кожен; дати тип події, джерело та суть. Для довгих даних — шлях до файла.
3. **Тримати стан у файлі.** Перший запуск тихий, наступні відрізняють нове від уже побаченого.
4. **Передавати винятки regex при запуску.** Відомий шум не потребує правки коду.
5. **Перевіряти «процес живий» у тому самому сторожі.** Не створювати окремі регулярні пробудження для здоров'я процесу.
6. **Не викликати LLM усередині.** Фільтрація та очікування — звичайний код.
7. **Не слати повідомлень.** Сторож read-only щодо джерел; його результат — локальний вивід і стан.

## 7. Антипатерни

- `ScheduleWakeup` або cron кожні N хвилин із завданням чату «подивитись».
- Читання Telegram через MCP на кожному tick, навіть коли повідомлень немає.
- Скріншоти для перевірки джерел, доступних скрипту як повідомлення або логи.
- Сторож, який знаходить подію, але не виходить: чат ніколи не прокинеться від його завершення.
- Сторож, який виходить на кожен рядок логу: звичайний шум перетворюється на пробудження.
- Дублювання слотів: одночасно `tick.sh` та `--until` для того самого статусу.

- [ ] Передати відомі винятки через `IGNORE`, перевірити розмір виводу: ≤ 10 рядків.
- [ ] Додати в `CLAUDE.md` проєкту правило з `feedback-no-periodic-wakeups`: «чат чекає лише через сторожі».
- [ ] Прибрати періодичні пробудження «перевірити Telegram і фабрику».
- [ ] Перевірити тихий перший запуск, одну реальну подію, завершення та повторний запуск.

Готовність: скрипти чекають самі; чат отримує коротку причину пробудження, діє та знову запускає сторож.
